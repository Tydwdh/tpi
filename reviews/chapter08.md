## 2. 亮点（证据层的扎实基础）

1. **不可变原始轨迹**：session JSONL append-only 事件日志正是书中「原始证据层保存只增不改的对话、轨迹和原始文档」——这是持续进化的前提，TPI 已具备。
2. **结果验证独立于模型声明**：eval 用 Bash 断言/文件状态检查验收，「模型声称完成不算数」——对应书中「判定交给模型写不了的验证」与「承诺—行动一致性」的评估侧实现。
3. **过程验证已有雏形**：ProgressTracker（无进展拒绝）+ 路径边界（越权拒绝）+ 预算熔断——即书中「过程验证器检查业务规则、权限和动作序列」的 Harness 侧实现。
4. **plan = 任务内「程序」载体**：`update_plan` 是唯一由模型驱动的结构化状态更新（可追溯、可修订），近似书中「结构化上下文」载体的最小形态。

## 3. 差距与建议（按优先级）

### 3.1 无离线进化循环（最大差距，但可选）

- **书中要求**：双循环——在线执行只记录证据，离线进化聚合轨迹、诊断根因、生成更新提案、验证后发布。最低成本起步是「经验沉淀为知识文档」。
- **TPI 现状**：运行结束即止；session 可回看，但无任何自动归纳。AGENTS.md 依赖用户手工维护。
- **评估**：个人 coding agent 场景，用户就是进化循环的人工版（阅读失败、手工改 AGENTS.md/system prompt）。自动进化价值有限，但「从已验证轨迹生成经验文档」是书中反复强调的最轻量增量。
- **建议最小切入**：①eval 失败任务 → 生成结构化 bad-case 摘要（首次错误步骤/工具/证据，第六章 3.3 同源）；②可选：`tpi` 提供命令把 N 次成功/失败轨迹归纳为 AGENTS.md 追加提案（仅提案，用户批准后合入，对应书中「待验证能力与正式能力隔离」）。

### 3.2 质量验证层缺失（LLM Rubric）

- **书中要求**：三层验证——结果（环境真值）、过程（规则/权限）、质量（LLM Rubric，逐项给分引用证据）；「结果与过程是硬门，都通过时语言质量才有资格决定候选是否值得学习」。
- **TPI 现状**：结果 ✅、过程 ✅、质量 ❌。eval 只有确定性断言。
- **建议**：与第六章 3.1 合并——expected.toml 支持可选 rubric（维度+veto），eval 后调用 judge LLM；veto 先由确定性检查触发。只有具备质量层，才能评价「是否办得合适」并支撑 3.1 的经验筛选。

### 3.3 安全边界需前置设计（若引入自动学习）

- **书中要求**：①证据与指令隔离（外部内容摘要不是净化，不能直接进 Skill）；②待验证与正式能力隔离（沙盒/扫描/审批）；③安全机制不可自我修改（验证器/测试/发布门槛/审计日志不可被 Agent 修改）。
- **TPI 现状**：无自动学习，暂无此风险；但若按 3.1 引入自动记忆/经验，这三条边界必须先建。
- **提醒**：TPI 的 eval 断言若可被未来学习流程修改，等于删除了可信根——建议 eval 验证器代码保持独立于任何自动更新路径。

## 4. 反叙事设计备注

**无自我修改是当前正确选择**：书中「Agent 修改自己的代码必须经隔离分支→静态检查→测试→灰度」——TPI 不自我修改，规避了整条风险链。个人工具的生命周期由开发者（用户）控制更合理。唯一可考虑的是「AGENTS.md 提案」这种最小、可审查、人工批准的进化形态（3.1）。
