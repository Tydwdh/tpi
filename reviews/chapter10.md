## 2. 亮点（单 Agent 侧的对策）

1. **「新信息判据」的反向印证**：书中「审核者使用测试执行结果审查代码 = 显著提升，因为引入执行反馈新信息」——TPI 把这一收益内化为单 Agent 循环：bash 跑测试 → 结果回传 → 模型修正。无需第二 Agent 即获得书中判定为「值得多 Agent」的核心增量。
2. **过早终止对策已在单 Agent 内建**：ProgressTracker（无进展拒绝）+ eval 独立验收（模型声明不算数）+ system_prompt「没有证据时不得声称已修复」——正是书中 Loop 工程「模型可以提出完成，但不能批准自己的完成」在单 Agent 的落实。
3. **理解债缓解**：TUI 全程透明（思考卡片/工具卡片/实时 diff/计划视图），用户可审查每一步——书中「管理 Agent 就像管理技术员工，需要理解而非外包」在个人工具场景的对应。

## 3. 差距与建议

### 3.1 无子 Agent/并行（合理缺席，但可留意）

- **书中要求**：子 Agent 隔离大体积中间信息（「隔离优于压缩」，第二章）+ 并行探索。
- **TPI 现状**：单 Agent 串行。
- **评估**：个人终端 coding agent 任务通常串行依赖（读→改→测），并行收益低；「隔离优于压缩」可由第二章已实现的 compaction/prune 部分替代。
- **建议（若未来引入）**：最小形态是 `spawn_subagent` 工具（子 Agent 独立 session + 结构化摘要回传），配合现成的 session 基础设施（每子 Agent 一个 JSONL），成本可控；但当前无需求。

### 3.2 无提议者-审核者（与第四/五章同源，汇总性记录）

- 书中多 Agent 最经典应用是提议者-审核者（质量/安全双用途）；TPI 无第二 Agent，第四章 3.1 已列 Sidecar/审批缺失。此处确认：书中「审核者必须读取独立证据而非复述提议者解释」——若未来补 Sidecar，只读结构化字段即满足此要求。

## 4. 反叙事设计备注

**单 Agent 不是妥协而是判据使然**：书中明确「如果协作未引入新信息，多 Agent 与单 Agent 持平甚至更差（等预算下）」。TPI 通过工具执行反馈在单 Agent 内获得了「执行反馈新信息」，不满足引入第二 Agent 的条件。加 Agent 只会增加 token 成本与编排复杂度，违背「多 Agent 收益须覆盖数倍开销」的成本原则。
